# tests/mavlink: integration tests of the MAVLink transport

Unit tests live next to the code (`ara/com/mavlink/ut`, `ara/com/mavlink/client/ut`,
`platform/common/mavlink_daemon/code/ut`, `tools/model_generator/ara/mavlink/test_*.py`,
`tools/mavlink/*_test.py`). This directory holds the integration tests: a real **MavlinkDaemon**
(the `daemon_host` core, built by the `mavlink_daemon_binary` rule), the example applications `example_app` and `example_app2`, and a
ground station on `pymavlink`, joined through simulated radio links (ptys).

## Running

```sh
bazel test //tests/mavlink/...
```

`tshark` must be installed (without it `tshark_lua_test` fails). `pymavlink` comes from bazel.
Run heavy builds under `flock -o` and a separate `--output_base` for ARM.

## Topology

One "CPU" of the test is three processes: **`daemon_host`** (the production daemon core without
Execution Management, controlled by JSON lines: `stats` returns the counters of the links and of
the daemon, `stop` saves the signing state and exits), `example_app` (provides EngineService
instances 2 and 3) and `example_app2` (requires instance 2). The applications run with the mains
in `no_em_main_app*.cc`, which skip Execution Management. The daemon opens the links
(`serial_radio`) on one end of a `ChannelSim` pty, the ground station sits on the other. The
applications reach the daemon through a unix socket (`SRP_MAVLINK_DAEMON_SOCKET`).

## LinkStats on the real ipc

The unit tests drive the service through the daemon IPC (`daemon_ipc`); the path through the real
`ipc` (shared memory + `someip_demon`) needs Execution Management and is checked in QEMU rpi (or on a
target). Everything needed is one ready package, nothing has to be edited:

* `//tests/mavlink/link_stats_cpu:pkg`: a CPU with Execution Management, someip_demon, state_manager,
  logger, diag_demon and two applications:
  * `//tests/mavlink:link_stats_daemon`: the MavlinkDaemon under Execution Management with two test
    drivers on `MemoryRadio`: `test_stats_a` reports nothing, `test_stats_b` pushes
    `OnLinkStats{rssi = -71, noise = -110}` every 100 ms. Config (installed in the `etc` of the
    daemon as `mavlink_daemon_config.json`): `link_stats_daemon_config.json` (`radio_a` -> `test_stats_a`,
    `radio_b` -> `test_stats_b`, `stats_period_ms` 1000).
  * `//tests/mavlink/link_stats_app`: the client (`require` on `ipc`, `instance` 1). For every event it
    prints `LINKSTATS link=... valid=... rssi=... noise=... rx_ok=...`, and after it finds the service it
    calls `GetLinkStats` for `radio_b` and for `nie_ma`: `GETLINKSTATS ok link=radio_b ...` and
    `GETLINKSTATS error link=nie_ma ...` (also in the log context `LKST`, console and remote).
* `//tests/mavlink/link_stats_cpu:flash`: `flash_ecu` of the package to `192.168.10.101` (the address of
  the QEMU guest and of the test EC).

Commands (as for `test_cpu`; skill `srp-tools`, "QEMU on the host"; heavy steps under `agent-res`):

```sh
# 1. build the package for rpi (the QEMU image of the guest is built by bazel run below)
bazel build --config=rpi-platform //tests/mavlink/link_stats_cpu:pkg
# 2. network for QEMU (once, by the user: sudo): bazel run @srp_platform//tools/qemu:network_configure
# 3. QEMU rpi on the host (tap0), one instance; leave it running in its own terminal
flock -o -n <lockfile> bazel run @srp_platform//tools/qemu -- --console
# 4. flash the package into the guest (another terminal; the guest is 192.168.10.101)
bazel run --config=rpi-platform //tests/mavlink/link_stats_cpu:flash
# 5. reboot the guest (the console shows `reboot`), wait for em/state_manager (~45 s), watch the console
#    (or `ssh root@192.168.10.101` and read the application log)
```

Expected within about 1.2 s after both applications are up, every `stats_period_ms` (1 s):

1. Two `LINKSTATS` lines per period: `link=radio_b` with `valid=3 rssi=-71 noise=-110` and `link=radio_a`
   with `valid=0`. **In this scenario nobody injects frames into the radios, so `rx_ok=0` on both
   links** (the counters are checked by `StatsTest`, where the test injects frames).
2. `GETLINKSTATS ok link=radio_b ...` equals the last `LINKSTATS` of `radio_b` (rssi -71, noise -110,
   `idx=1` as `radio_b` is second in the config file); `GETLINKSTATS error link=nie_ma`.
3. Restart the daemon (`kill` of `mavlink_daemon`; Execution Management starts it again): the client finds
   the service again and the events resume within a few seconds.

FAIL: no `LINKSTATS` line (the client did not find the service: check that `mavlink_daemon` and `link_stats_app`
both run and the log of the daemon, `MAVD`), `valid=0` on `radio_b`, `rx_ok` other than 0.

Isolation of two CPUs: `ipc` is local to the CPU (shared memory of the machine and a local
`someip_demon`), so a client sees only the daemon of its own CPU; the paths cannot be overridden on one
machine, so that is checked at the `daemon_ipc` layer (two daemons with their own sockets, each client sees only its own links:
`StatsTest.TwoDaemonsWithOwnSocketsShowEachClientOnlyItsOwnLinks`).
